# SyncCampus
## Complete Website Logic & Functional Specification

---

# 1. What SyncCampus Is

SyncCampus is a centralized college management platform that keeps **students, teachers, administrators, classrooms, lectures, timetables, examinations, and announcements synchronized in one system**.

The main problem it solves is information fragmentation.

Today, a timetable change might be communicated through:

- WhatsApp groups
- Verbal communication
- Notice boards
- Class representatives
- Teacher messages
- Separate PDFs
- College announcements

This can cause confusion.

SyncCampus creates one central source of information.

### Core principle

> **One change in the system should automatically reach every person affected by that change.**

For example:

```text
Teacher changes classroom
        ↓
SyncCampus validates the change
        ↓
Central timetable is updated
        ↓
Student timetable updates
        ↓
Affected students receive notification
        ↓
Admin can see the activity
```

---

# 2. Three Types of Users

SyncCampus has three primary roles:

```text
                    SYNC CAMPUS
                         │
                  Email + OTP Login
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       STUDENT         TEACHER         ADMIN
          │              │              │
        VIEW        VIEW + MANAGE    FULL CONTROL
```

Each account has a specific role.

## Student

Students primarily consume information.

They can:

- View their timetable
- View today's classes
- View upcoming classes
- View classrooms
- View teachers
- Receive notifications
- View announcements
- View examination schedules
- View timetable changes

They cannot modify official academic information.

---

## Teacher

Teachers can view their assigned timetable and manage lectures assigned to them.

They can:

- View their timetable
- Cancel their lecture
- Request or perform permitted rescheduling
- Change classroom where permitted
- View assigned classes
- Receive notifications
- View announcements

They cannot modify another teacher's lectures or system-wide academic information.

---

## Admin

Admin has complete control.

Admin can:

- Manage students
- Manage teachers
- Manage classrooms
- Manage departments
- Create timetables
- Edit timetables
- Reschedule lectures
- Cancel lectures
- Assign teachers
- Assign classrooms
- Manage examinations
- Publish announcements
- Manage user accounts
- View system activity
- Resolve conflicts

---

# 3. Authentication Logic

SyncCampus should use **email OTP authentication** rather than traditional passwords.

## Login Flow

The first page displays:

**Student Login**

**Teacher Login**

**Admin Login**

The user selects their role.

Then:

```text
Select Role
     ↓
Enter Email
     ↓
System checks account
     ↓
OTP generated
     ↓
OTP sent to registered email
     ↓
User enters OTP
     ↓
OTP verified
     ↓
Role verified
     ↓
Dashboard opened
```

---

# 4. Email Verification Rules

The system should not allow anyone to select a role and access that role's dashboard simply by entering an email.

The account must already exist and have a defined role.

Example:

```text
student@gmail.com
Role = Student
```

If that person selects **Admin Login**, the system should not give them admin access.

Instead:

> This account is registered as a Student account.

The user should be redirected to the correct login flow.

---

# 5. OTP Logic

When an OTP is requested:

- Generate a temporary OTP
- Send it to the registered email
- Set an expiry time
- Allow limited verification attempts
- Invalidate the OTP after successful verification
- Invalidate the previous OTP when a new OTP is generated

Example:

```text
OTP: 482931
Valid for: 5 minutes
Attempts: Limited
```

If the OTP expires:

> OTP expired. Please request a new OTP.

If the user enters an incorrect OTP:

> Incorrect OTP. Please try again.

Repeated failed attempts should temporarily block further attempts to protect the account.

---

# 6. Dashboard Selection

After successful authentication:

```text
Student → Student Dashboard

Teacher → Teacher Dashboard

Admin → Admin Dashboard
```

The dashboard should be generated according to the user's role and assigned data.

A student should never receive teacher/admin controls simply by manipulating the URL or frontend.

Permissions must be enforced by the system itself.

# 7. Central Data Structure

The most important concept is that SyncCampus should have a **central source of truth**.

The timetable should not exist separately for students and teachers.

There should be one official lecture record.

For example:

```text
Lecture ID: LECTURE_1042

Subject:
Database Management System

Teacher:
Prof. Rahul Sharma

Course:
BSc IT

Semester:
3

Division:
A

Date:
Monday

Start:
10:00 AM

End:
11:00 AM

Room:
204

Status:
Scheduled
```

The student and teacher dashboards simply display the relevant information from this central record.

---

# 8. Why a Central Timetable Is Important

Do NOT create:

```text
Student Timetable
Teacher Timetable
Admin Timetable
```

as completely separate information.

Instead:

```text
                 CENTRAL LECTURE
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       Student       Teacher       Admin
       View          View          Manage
```

This prevents inconsistent information.

If the room changes from 204 to 305, everyone reads the same updated lecture record.

# 14. Timetable Conflict Detection

This is one of the most important backend rules.

A lecture should not be created if it creates a conflict.

The system should check at least four things.

## Conflict 1: Teacher Conflict

Example:

Prof. Rahul Sharma already has:

10:00–11:00 → DBMS

Admin tries to assign:

10:00–11:00 → Java

Result:

> ⚠️ Teacher Conflict  
> Prof. Rahul Sharma is already assigned to another lecture during this time.

---

## Conflict 2: Classroom Conflict

Room 204 is already occupied:

10:00–11:00 → Web Development

Admin tries:

10:00–11:00 → DBMS → Room 204

Result:

> ⚠️ Classroom Conflict  
> Room 204 is already occupied during this time.

---

## Conflict 3: Division Conflict

BSc IT Semester 3 Division A already has:

10:00–11:00 → DBMS

Admin tries to schedule another lecture for the same division:

10:00–11:00 → Java

Result:

> ⚠️ Division Conflict  
> This class already has a lecture during this time.

---

## Conflict 4: Exam Conflict

If an examination is scheduled in Room 204:

10:00–1:00

The system should not allow a regular lecture to use that room during the same period.

**Completed**

# 26. Teacher Permissions and Approval

A practical rule should be used for teacher changes.

Teachers can directly make changes to their assigned lectures **only where the college permits it**.

For more sensitive changes, such as moving a lecture to another day or making a change that affects another timetable, the system can use:

```text
Teacher submits change
        ↓
Admin reviews
        ↓
Approve / Reject
```

If approved:

```text
Central timetable updates
↓
Students notified
```

If rejected:

```text
Teacher receives:
"Your schedule change request was rejected."
```

This gives the college flexibility in how strict its approval process is.

- All relevant users

- Relevant teachers

# 40. No Internet / Temporary Connection Issue

The interface should handle temporary network failures gracefully.

If a user performs an action while the connection fails:

> Unable to save changes. Please check your connection and try again.

Do not show:

> "Success"

until the server confirms that the change was actually saved.

This is especially important for timetable changes.

---

# 41. Double-Click / Duplicate Action Protection

Suppose an admin clicks:

**Create Lecture**

twice quickly.

The system should not create two identical lectures.

After the first request is submitted:

**Creating lecture...**

Disable the button temporarily until the operation completes.

The same applies to:

- Cancel
- Reschedule
- Change room
- Publish announcement
- Publish exam

---

# 42. Two Admins Editing the Same Lecture

Scenario:

Admin A opens DBMS.

Admin B also opens DBMS.

Admin A changes room:

204 → 305

Admin B then tries to change:

204 → 306

The system should detect that the lecture has changed since Admin B opened it.

Show:

> This lecture was updated by another administrator. Please refresh and review the latest information.

This prevents one admin from accidentally overwriting another admin's changes.

---

# 43. Teacher and Admin Editing at the Same Time

Scenario:

Teacher requests:

DBMS → 2 PM

At the same time, Admin changes DBMS → 3 PM.

The system should use a controlled update process.

The admin's latest authorized decision should determine the final official timetable, while the teacher should receive an update if their requested change was overridden.

---

# 47. Role-Based Security

The system must enforce permissions on the server.

For example:

A student should not be able to access an admin endpoint simply by changing:

```text
/student/dashboard
```

to:

```text
/admin/dashboard
```

The server must verify:

```text
User authenticated?
        ↓
What is user's role?
        ↓
Does role have permission?
        ↓
Allow / Reject
```

---

# 48. Logout

When the user clicks Logout:

```text
Session terminated
↓
Return to login page
```

Protected dashboard pages should no longer be accessible through the previous session.

---

# 49. Account Deactivation

If an admin deactivates a teacher:

```text
Teacher Status:
Active → Inactive
```

The teacher cannot log in.

Existing timetable records should not simply disappear.

Instead, the admin should be warned:

> This teacher has 12 upcoming lectures assigned.

The admin should reassign those lectures before completely removing the teacher.

---

# 50. Student Promotion / Semester Change

At the end of an academic year, students may move from:

```text
Semester 2 → Semester 3
```

The system should allow admins to update academic assignments in bulk.

Example:

```text

Semester 2
Division A

↓ Promote

Division A
```

The student's new timetable should automatically follow the new academic assignment.

---

# 51. Academic Year

The system should understand academic years.

Example:

```text
2026–27
```

Timetables, students, teachers, and exams should be associated with the correct academic year.

This prevents old timetable data from mixing with the current academic year.

# 63. Important Rule: Never Duplicate Official Information

For example, do not create separate copies of:

```text
DBMS Room 204
```

for every student.

Instead:

```text
Lecture L1042
      ↓
72 affected students
      ↓
1 teacher
```

All of them reference the same official lecture.

This is what makes synchronization reliable.

# 65. The Most Important Logic of SyncCampus

The entire product can be summarized in five principles.

### 1. One Source of Truth

The official timetable exists centrally.

### 2. Role-Based Access

Students, teachers, and admins see different controls.

### 3. Automatic Synchronization

One approved change updates everyone affected.

### 4. Conflict Prevention

The system checks for timetable, teacher, classroom, division, and examination conflicts before saving changes.

### 5. Traceability

Important changes are recorded so the system knows:

**Who changed what, when, and from what to what.**

# 67. Final Product Vision

SyncCampus should not feel like three separate websites.

It should feel like **one connected campus system with three different levels of access**.

```text
                    SYNC CAMPUS
                         │
               ┌─────────┴─────────┐
               │ CENTRAL SYSTEM    │
               │                   │
               │ Timetable         │
               │ Users             │
               │ Classes           │
               │ Classrooms        │
               │ Exams             │
               │ Announcements     │
               │ Notifications     │
               │ Activity History  │
               └─────────┬─────────┘
                         │
           ┌─────────────┼─────────────┐
           ↓             ↓             ↓
        STUDENTS       TEACHERS       ADMIN
           │             │             │
          VIEW       MANAGE OWN     MANAGE ALL
                       LECTURES
```

The most important idea is:

> **If information changes once, SyncCampus should make sure the correct people see that change everywhere.**

That synchronization is the actual core of the product, not just the timetable UI.
